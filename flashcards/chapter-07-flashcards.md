## Chapter 7: Agents, the Agent Store, and Microsoft Foundry at a Leadership Level — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Agent Store — leadership purpose? | Lets business leaders discover, vet, and deploy pre-built agents quickly without custom development. Exam tip: choose Agent Store when the need matches an existing agent and speed matters. |
| 2 | Microsoft Foundry — leadership purpose? | Platform for building custom/advanced AI solutions (custom models, proprietary data, multi-system orchestration). Exam tip: choose Foundry when requirements are highly specific or no pre-built agent fits. |
| 3 | Copilot chat vs Agent — core difference? | Copilot chat responds turn-by-turn to user prompts. Agents can execute multi-step tasks autonomously or semi-autonomously and can be triggered by events/schedules, not just active chat. |
| 4 | Autonomous agent vs semi-autonomous agent? | Autonomous: completes tasks end-to-end without human checkpoints. Semi-autonomous: performs multi-step work but pauses for human approval at defined points (human-in-the-loop). |
| 5 | Foundry vs Foundry Tools — what's the relationship? | Foundry is the overall platform for building/deploying AI solutions and agents. Foundry Tools are the pre-built AI capability building blocks (vision, language, speech, document intelligence) used within Foundry. |
| 6 | Pre-built agent vs custom-built agent — when to pick each? | Pre-built (Agent Store): common, well-defined business task, no dev team needed, fast deployment. Custom-built (Foundry): proprietary data/models, unique multi-system orchestration, dedicated dev resources available. |
| 7 | Vetting a third-party Agent Store agent — leadership checklist? | Check publisher verification status, data/permission scopes requested, and compliance certifications. Store presence alone does not remove the org's own review responsibility. |
| 8 | Human-in-the-loop pattern — when to require it? | Use for actions with financial, legal, or customer-impact risk (e.g., refunds, external communications) — agent drafts/prepares the action, a human approves before execution. |
| 9 | Signal that a need calls for a Foundry initiative, not an Agent Store agent? | Requirement involves a proprietary/custom-trained model, integration with internal proprietary systems, or orchestration logic no existing agent supports. |
| 10 | Signal that a need calls for an Agent Store agent, not a Foundry build? | The business need matches a common, well-known task (e.g., email drafting, meeting summarization), speed-to-value is a priority, and no dedicated dev team is available. |
| 11 | Governance control leadership should set when enabling the Agent Store tenant-wide? | Restrict which agents can be deployed and what data/permission scopes agents can access — do not allow unrestricted install rights or DLP bypass. |
| 12 | Risk consideration unique to third-party (non-Microsoft) agents? | Third-party agents may request broader data access or lack the same compliance transparency as Microsoft-built agents; leadership must independently verify publisher trust and permission scope before approval. |
